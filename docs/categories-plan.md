The tree is hand-authored directly (no longer generated by fetching MercadoLibre's live API into a seed file — see decision 4 below), so there's no separate generation step: root categories are added straight into a versioned seed JSON as they're decided.

## Why

Categories today are a flat, hardcoded 7-item enum (`Electronics | Clothing | Furniture | Vehicles | Books | Sports | Other`), duplicated by hand in three places. Users coming from MercadoLibre already know its category naming — taking inspiration from it (not mirroring or syncing it) gives them a taxonomy they recognize, and gives undermarket enterprise-grade filtering (hierarchical, denormalized for cheap Firestore queries) instead of a 7-bucket catch-all, without coupling our data model to MercadoLibre's own.

## Current state (why this isn't a from-scratch design)

- `category` is a flat closed-set string, kept in sync by hand across three files (per the comment at the top of each):
  - [`src/app/domain/category/category.model.ts`](../src/app/domain/category/category.model.ts) — the `CATEGORIES` const + `Category` type.
  - [`firestore.rules`](../firestore.rules) line 15, `isValidCategory` — exact match against the same 7 strings.
  - [`functions/src/mercado-libre/category-map.ts`](../functions/src/mercado-libre/category-map.ts) — a third, independent copy, since Cloud Functions is its own TypeScript project and can't import from the Angular app.
- undermarket already **imports listings from MercadoLibre**: [`functions/src/mercado-libre/import-listings.ts`](../functions/src/mercado-libre/import-listings.ts) runs an OAuth flow, fetches each item's ML category *name* via `GET /categories/{id}`, and keyword-matches that name (Spanish only) into one of the 7 buckets via `mapCategoryName`. This gets replaced by the AI classifier described in section 6, not by a richer keyword table.
- [`functions/src/mercado-libre/constants.ts`](../functions/src/mercado-libre/constants.ts) states outright: *"MercadoLibre Argentina only, per the app's currency/category scope."* — `ML_AUTH_HOST`/`ML_API_HOST` are already scoped to MLA (Argentina). This settles the taxonomy source: **seed from MLA**, matching the currency scope (ARS/USD) already enforced in `firestore.rules`.
- Consumers of the flat enum today: [`new-listing.ts`](../src/app/features/listings/new/new-listing.ts) (required select field), [`discover.ts`](../src/app/features/discover/discover.ts) (chip-row filter), [`search.ts`](../src/app/features/search/search.ts) (dropdown filter), [`firestore-listing.repository.ts`](../src/app/infrastructure/firebase/firestore/firestore-listing.repository.ts) (`where('category', '==', ...)`), and a composite index in [`firestore.indexes.json`](../firestore.indexes.json) (`category` + `createdAt` + `status`). Every one of these needs to change.

## Decisions (resolved)

1. **Depth** — capped at 3 levels (root → depth1 → depth2 leaf). Confirmed.
2. **Curation** — this platform allows service listings, not just goods resale, so `services` is a hand-authored root category from day one, alongside goods-oriented roots like *Electronics*, *Vehicles*, *Home & Furniture*, etc. There's no MLA include/exclude list to apply anymore (see decision 4) — every root is a deliberate, hand-picked addition.
3. **Translation** — both `es` and `en` names are authored directly (not imported from any source); `en` naming is cross-checked against how Vinted/eBay/Amazon name their own equivalent categories, so a shopper coming from any of those recognizes it immediately.
4. **Relationship to MercadoLibre (and any other provider)** — the tree is **not** synced from or structurally derived from ML's taxonomy. It's our own design, only *inspired* by ML's (and Vinted's/eBay's) category naming for familiarity. Reasons: (a) reducing/curating leaves would otherwise leave "missing" ML categories with nowhere well-defined to go, (b) baking ML's numeric `category_id`s into our node data would couple our taxonomy to one provider, which breaks the moment a second integration (eBay, Vinted, ...) needs the same tree, (c) ML's own tree changes over time and "keeping in sync" isn't a goal — our categories, our decisions. Mapping an external provider's category onto one of our nodes at import time is handled by a best-effort AI classifier with a cache (see section 6), not by a field stored on the node.


## 1. Taxonomy & data model

New flat collection **`categories/{categoryId}`** (flat + a `parentId` field, not nested subcollections — this is what makes both "all children of X" and "the whole tree in one read" cheap in Firestore):

```
categoryId    string   // our own stable kebab-case slug, e.g. "cell-phones"
parentId      string | null
path          string[] // ancestor ids root→leaf, INCLUDING this id
depth         number   // 0 = root
order         number   // sibling display order
icon          string   // ul-icon name, for chip/tree UI
isActive      boolean  // soft-deprecate instead of delete — listings reference these forever
isLeaf        boolean  // whether new listings may be filed directly under it
createdAt / updatedAt / updatedBy   // audit trail, same convention as Listing
```

Display names are **not** stored on the doc. They live in `en.json`/`es.json` as `category.<categoryId>`, resolved through Transloco like everything else in the app — renaming a category becomes a normal i18n PR, not a data migration, and the doc and its translation can't drift apart.

No field on the node references any external provider (see decision 4) — the tree stays reusable across every current and future listing-import integration, not just MercadoLibre.

## 2. Listing schema change

Replace the single `category: Category` field with:

```
categoryId    string     // leaf category
categoryPath  string[]   // root→leaf ancestor ids, denormalized from the category doc at write time
```

`categoryPath` is the standard Firestore pattern for hierarchical filtering without joins: "everything under Electronics" becomes `where('categoryPath', 'array-contains', 'electronics')`, regardless of which leaf a listing actually sits in.

Keep the legacy `category` string field alongside the new ones during migration (Phase 4); remove it only once every reader/writer is confirmed on the new fields (Phase 7).

## 3. firestore.rules

- Replace `isValidCategory`'s hardcoded array with a check that `categoryId` is a non-empty string and `categoryPath` is a non-empty array of strings whose last element equals `categoryId`. No cross-doc read needed.
- Optionally also gate on the category existing and being active via `get(/databases/$(database)/documents/categories/$(categoryId)).data.isActive == true` — costs one `get()` per write (rules allow up to 10 per evaluation); confirm this is acceptable against existing Firestore quota/latency patterns before committing to it.
- New `categories/{id}`: `allow read: if true; allow write: if false` — same posture as other Admin-SDK-only fields in this app (e.g. `onboarded`): categories are edited only by seed/migration tooling via the Admin SDK, never by a client.
- Update the sync-comment at the top of `firestore.rules` to point at the new model file instead of the old one.

## 4. firestore.indexes.json

The existing `category + createdAt + status` composite index gets replaced with an equivalent built on `categoryPath` (array-contains) + `createdAt` + `status`. Let the Firebase CLI's own error on first deploy dictate the exact required index shape rather than guessing it by hand — array-contains + orderBy composites have specific rules.

## 5. Seed pipeline (offline tooling, not a client-facing path)

1. **Author**: build the tree directly, root by root — no external fetch step. Each node gets its own `categoryId`/`parentId`/`path`/`depth`/`order`/`icon`/`isLeaf`, decided by hand (optionally glancing at ML/Vinted/eBay for naming/structure inspiration, per decision 3).
2. **Translate**: `es` and `en` names are authored together for each node (not imported), added to `en.json`/`es.json` as `category.<categoryId>` in lockstep (same key, same position in both files).
3. **Commit as data**: write the result as a versioned JSON file in the repo (e.g. `functions/src/categories/seed/categories.v1.json`) — reviewable and diffable in a PR, not just a live Firestore export nobody can inspect.
4. **Seed script**: an Admin-SDK, human-run script (not a callable Cloud Function — no client-facing path needed) that upserts the JSON into `categories/{id}`, idempotent by our own slug. **Never hard-deletes** — a category missing from a newer snapshot gets `isActive: false`, since listings may still reference it.

## 6. Migration of existing data

- **Done**: `Listing.categoryId?`/`categoryPath?` added alongside the legacy `category` field (`src/app/domain/listing/listing.model.ts`), read through in `firestore-listing.repository.ts`'s `mapDoc`. `functions/src/categories/legacy-category-map.ts` holds the 7-entry mapping (each legacy value → one specific leaf id — lossy by design, see its own comment); `functions/src/categories/backfill-listings.ts` (idempotent, `bulkWriter`, run via `npm run backfill:listing-categories` from `functions/`) sets `categoryId`/`categoryPath` on every listing doc that doesn't have them yet, without touching `updatedAt`. Required adding one new leaf, `other-miscellaneous`, since `other` had no plain leaf of its own once it grew the 5 nested groups. New listings created through the current (still-legacy) `new-listing` form won't get these fields until phase 6 ships the picker — this backfill only covers what already existed at the time it's run; re-running it later picks up anything created in between.
- **Done**: `functions/src/mercado-libre/category-map.ts` (the keyword matcher) is gone; `functions/src/categories/category-map.ts` now exports `classifyCategory(provider, externalCategoryId, externalCategoryName, listingTitle)`, called from `import-listings.ts`. It loads the active-leaf list (`categories` where `isActive && isLeaf`) plus their Spanish names (read straight from `public/assets/i18n/es.json`, memoized per warm instance), and calls **Vertex AI Gemini** (`gemini-flash-lite-latest`, via `@google/genai`'s `GoogleGenAI({vertexai: true, project, location: 'us-central1'})`) with `responseMimeType: 'application/json'` + a `responseSchema` whose `categoryId` field is an `enum` of the real leaf ids — so the model can't return an invalid id. Auth is Application Default Credentials — the Cloud Function's own runtime service account, no API key/secret to manage (this is why Vertex AI was chosen over a directly-called third-party LLM API: one less secret, same IAM boundary Firestore Admin access already uses). Any failure (API error, malformed response) falls back to `other-miscellaneous` **without** writing the cache, so a transient failure just gets retried on the next listing in that category rather than sticking. **Before this runs in prod**: the Vertex AI API needs to be enabled on the GCP project, and the Cloud Functions runtime service account needs the `roles/aiplatform.user` IAM role — both one-time console/`gcloud` steps, not code.
  - **Cache by external category, not per listing**: `categoryClassifications/{provider}:{externalCategoryId}` → `{ categoryId, updatedAt }` (Admin-SDK-only, see `firestore.rules`). First listing seen in a given ML category pays the LLM call; every later one is a cache read. A newly-appearing ML category is just a cache miss — no manual sync step, ever. Wrong mappings are corrected by deleting the one cache doc, forcing re-classification on the next import.
  - `import-listings.ts` still also sets the legacy `category` field (via the new `NEW_ROOT_TO_LEGACY_CATEGORY` reverse table in `legacy-category-map.ts`, root → closest of the 7 old buckets) — imported listings land as `status: 'draft'`, invisible to any public/filtered query until the owner reviews and publishes, but keeping `category` populated avoids a blank legacy field if that publish flow still reads it before phase 6 ships.
  - Same mechanism works for any future provider (eBay, Vinted, ...): swap what's fed to the classifier, keep the cache/fallback pattern.
- `category-map.spec.ts` (in `functions/src/categories/`) tests the classifier with the SDK and Firestore mocked — cache hit, cache miss + cache write, API failure fallback, malformed-response fallback, and the missing-fallback-leaf guard.

## 7. Client-side surfaces

Each of these is its own change, not a side effect of the schema change:

- New `CATEGORY_REPOSITORY` DI token + Firestore implementation, matching the existing `LISTING_REPOSITORY`/`USER_REPOSITORY` pattern — fetches the whole tree once (a few hundred small docs) and caches it in a signal, since the taxonomy changes rarely.
- **new-listing**: flat `<ul-select>` of 7 options → a hierarchical picker. Very likely a **base UI gap** (no cascading-select/category-tree component exists yet) — per the project's standing rule, that gets built in base UI, not patched locally in undermarket.
- **discover**: the chip row of 7 doesn't scale to ~100+ categories — needs a "top-level chips, drill into children" or "browse categories" redesign. A UX decision, not an implementation detail.
- **search**: dropdown → hierarchical/searchable equivalent; filter logic changes from `category ==` to `categoryPath array-contains` (parent-level) or `categoryId ==` (exact leaf).
- **listing-detail**: the category pill currently shows the raw string; needs to resolve `categoryId` → localized breadcrumb via the new repository/i18n keys.

## 8. Enterprise-grade cross-cutting items

- Audit fields (`createdAt`/`updatedAt`/`updatedBy`) on every category doc, matching `Listing`'s own convention.
- A `version` marker (e.g. a `categories/_meta` singleton doc) so the seed script can tell "nothing changed" from "reconcile against a new snapshot."
- Tests: new repository, rules tests for the new `isValidCategory`/write-denial behavior, rewritten `category-map.spec.ts`.
- i18n tooling: `en.json`/`es.json` must stay identical in key set *and order* — adding 100+ `category.*` keys by hand invites drift, so this needs a small script step that inserts them into both files in the same order.
- Deferred/explicitly out of scope for v1: MercadoLibre-style per-category filter attributes (brand/size/year), and wiring categories into Algolia facets once that search backend lands (already a standing TODO elsewhere in the listing-detail work).
